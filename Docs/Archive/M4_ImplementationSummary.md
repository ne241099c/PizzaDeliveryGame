## 遊び方

1. `Assets/Scenes/SampleScene.unity` を開いてPlay。5分の営業が始まる。初回の注文は約17.5〜32.5秒後。
2. 左の注文を1〜2件選び、`Idle` の配達員を選ぶ。注文の数字は期限までの残り秒数。オレンジは急ぎ、黄色は選択中。
3. 地図のつながっている道、または右の `NEXT ROADS` を順番に押す。選んだ全配達先を通り、Storeまでの帰り道も組む。行きと帰りは違う道でもよい。
4. `Individual reference` は同じ配達員が各注文を別々に最短往復した参考時間。`Saves` は自作ルートで短縮できる秒数。合計・参考時間・道路候補の表示はすべて移動倍率を適用した秒数。
5. `Dispatch` で出発。押した時点では得点は入らない。地図の `[M]` / `[A]` / `[R]` が進み、配達先に着いたときに得点が入る。
6. その間に別の注文と待機中の配達員で次のルートを組める。帰還すると `Idle` に戻る。
7. 忙しいときは `Dispatch with suggestion` で推奨ルートのまま即出発。右下の `Optional suggestion` は道順を編集欄に入れるだけなので、適用後も自由に修正できる。
8. 閉店で待機注文はキャンセル。出発済みの人が全員帰ると結果画面。`Play again` で時計・注文・得点・配達員を初期化する。

履歴・道路候補・注文リストはスクロール可能。地図はホイールでズーム、中ボタンのドラッグで移動、`Fit` で全体表示。`Reset` は営業中も最初からやり直す。

### 判断の例

- 2件をまとめれば往復を減らせるが、次の注文を待ったり、道を組んだりする間にも時計は進む。
- 期限が近い注文を先に回るか、効率よくまとめるかを選ぶ。
- Ren (0.3) は裏道の技能ペナルティが大きい。Goal1→Goal2のまとめ配達で大通り往復は約36.7秒、裏道往復は約42.1秒。Minato (0.9) は同じ裏道ルートが約34.3秒。
- 比較相手は「個別の参考時間」。推奨ルートは既存の探索で最短を求めるため、自分で組めば必ず推奨より速くなる、というルールではない。

## 調整する場所

Hierarchy の `GameManager` を選び、Inspectorで変更する。保存したい調整はPlay停止中に行う。

| Component / 項目 | 初期値 | 効果 |
|---|---|---|
| GameClock / Business Duration | 300 | 営業時間 |
| GameClock / Travel Time Multiplier | 5 | M3の移動時間から秒数への倍率。UnityのTime.timeScaleとは別 |
| GameClock / Planning Time Rate | 1 | 注文と配達員を選択している間の時計速度。厳しければ0.3等に下げる |
| OrderSpawner / Interval | 25 | 注文間隔。短いほど忙しい |
| OrderSpawner / Interval Variation | 0.3 | 間隔の±30%変動 |
| OrderSpawner / Deadline Factor | 1.8 | 期限の余裕。下げると厳しい |
| ScoreManager / Score Per Delivery | 100 | 基本点 |
| ScoreManager / Late Penalty Per Second | 5 | 遅れ1秒ごとの減点 |
| ScoreManager / Closing Cancellation Penalty | 0 | 閉店キャンセル1件の減点 |
| OrderListUI / Urgent Seconds | 15 | 期限表示をオレンジにする秒数 |
| DeliveryPersonSelector / Delivery People | 3人 | 名前・スキル。M4では既定の3人で確認 |

期限は「発生時刻＋スキル1.0の最短往復時間×移動倍率×期限係数」。Goal1の猶予は54.9秒、Goal2は58.5秒。
得点は `max(0,100−遅延秒×5)` を整数へ四捨五入（0.5切り上げ）する。未出発の注文は期限の20秒後にキャンセル。出発済みの注文は0点でも配達を続ける。
減点/秒を0にした場合、時間超過キャンセルは行わず、閉店時にはキャンセルする。

## コードの役割

| ファイル | 役割 |
|---|---|
| GameClock.cs | 唯一の時間源。営業開始・閉店・終了と時計の進みを通知 |
| OrderSpawner.cs / Order.cs | 自動発注、期限、注文の状態 |
| DeliveryTrip.cs | 出発時の道順・各到着時刻・移動位置を保存 |
| DeliveryFlowController.cs | 出発、並行配達、到着採点、帰店、キャンセル、営業終了 |
| DeliveryPerson.cs / DeliveryPersonSelector.cs | 配達員の状態と選択・残り帰還時間 |
| DeliveryScoring.cs / ScoreManager.cs / DayStats.cs | 得点の計算、画面反映、日次集計 |
| DeliveryMarkerView.cs | 地図上の配達員の移動表示 |
| DeliveryPlannerUI.cs / OrderListUI.cs | 道順編集、比較、各ボタン、注文・期限の表示、結果画面 |
| EditorPreviewOnly.cs | 停止中に地図を見せるプレビュー。PlayではMapManagerの実地図に切り替え |
| Editor/M4SceneSetup.cs | SceneにUIを配置する編集時専用ツール。再実行するとCanvasのレイアウトを作り直すため通常は不要 |
| Editor/M4Validation.cs / M4PlayValidation.cs | 計算の検証と実際のUIイベントを使った営業フローの検証 |

`ManualDeliveryRoute`、`RoadPathfinder`、`MapManager` は変更していない。静的UIはSampleSceneの1つのCanvasに保存し、各スクリプトがInspectorの参照から操作する。実行中に作るのは注文・道路の可変行と配達員の目印。
地図の停止中プレビューは編集時のスナップショット。MapDefinition等を変更した場合はプレビューも再作成する必要がある（Play中の地図はMapManagerが最新データを使用）。

## 検証

Play中に `Tools > Pizza Delivery` から実行できる。

- `Validate M3 Sample`：既存41項目。自由経路、比較、スキル、推奨探索、一方通行。
- `Validate M4`：35項目。期限式、満点/遅延/0点/端数、同住所2件、移動位置、出発時の固定、時刻境界、日次集計。
- `Validate M4 Day Flow`：21項目。**出発していない新しいPlayで、最初の注文が発生してから100秒以内に実行する。検証用注文に入れ替え、時計を進めてその営業を終了する。** 手動ボタンでまとめルート→3人同時出発→到着採点→帰還→期限切れ→閉店→最後の帰還→結果までを確認する。
- 統合検証の結果：配達5件、遅延1件、キャンセル2件、得点412。`Play again` による初期化も別途確認。
- 計97項目PASS、Unityのコンパイルエラー・警告なし。
- Sceneを保存して再読込し、UI参照の欠落なし、Canvas1つを確認。停止中のUIが描画されなくなった際はUnity再起動で復旧した。診断のためのカメラ・Canvas・Editorスクリプトは残していない。再起動後も97項目の検証を再実行してPASS。

通常速度の5分通し確認の結果と、残る調整判断は下記に記録する。

### 通常速度での通し確認（2026-10-22）

時計を早送りせず300秒営業し、閉店後の最後の帰還で約319.4秒時点に終了した。操作は検証用の一時スクリプトから画面と同じボタンイベントを呼び、道を1秒に1本組む方式。初回は2件を待ってまとめ、以降は注文を8秒以上読んでから、3人を順番に使った。地図の目印と結果画面も確認した。これは人間の感想を代替するテストではない。

| 結果 | 値 |
|---|---|
| 出発 | 9回（まとめ1回） |
| 配達 / 遅延 | 10件 / 0件 |
| キャンセル | 1件（閉店時に未出発） |
| 得点 | 1000 |
| 最大同時配達 / 最大待機注文 | 2人 / 2件 |
| まとめでの参考時間との差 | 約31.3秒短縮 |

初期値は変更していない。注文25秒間隔に対して移動が30〜36秒程度なので、3人を常に忙しくするほどの負荷はない。期限にも余裕があり、この通し確認では全配達が満点だった。
改善の候補は、まず `Interval` を18〜20秒程度に下げること。その後も遅延が出なければ `Deadline Factor` を少し下げて比較する。これらはまだ検証した採用値ではない。操作の負担や「まとめるか今出すか」の面白さは、本人が実際に触って判断する。M4-7の最終調整は残っている。
