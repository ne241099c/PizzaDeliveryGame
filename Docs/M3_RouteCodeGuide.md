# M3のルート処理を読むためのガイド

## 最初に押さえる役割

| ファイル | 担当すること |
|---|---|
| `ManualDeliveryRoute.cs` | プレイヤーが選んだ道順を記録し、成立するルートか確認する |
| `RoadPathfinder.cs` | 道路網から最短時間の経路を探す。推奨1件と個別配達の参考時間に使う |
| `DeliveryPlannerUI.cs` | クリックを受け取り、上の処理を呼び、画面へ表示する |
| `MapManager.cs` | 地点・道路の情報、接続、道1本の時間、地図の見た目を提供する |

手動で道順を作る処理と、コンピューターが参考経路を探す処理は独立している。
プレイヤーが道路をクリックしたときは `ManualDeliveryRoute.TryAppend` を使う。
そのクリックの行き先をDijkstra法が勝手に決めることはない。

## 1. ManualDeliveryRoute：選んだ道順を保存する

まずこのファイルを、フィールド → TryAppend → Undo → GetTime → BuildCompletion の順で読む。

### 保存する2つのリスト

```text
nodeIds: Store → N1 → N2 → Goal1
edgeIds:    道A → 道B → 道C
```

- `nodeIds` は通る地点の順番。最初の店舗も含む。
- `edgeIds` は通る道路の順番。
- 常に `nodeIds.Count == edgeIds.Count + 1` になる。
- `CurrentNodeId` はnodeIdsの最後。ルートを編集している位置を表す。
- 同じ道路を2回通るなら、edgeIdsにも2回保存する。往復分の時間を計算できる。

### TryAppend：次の道を1本追加

1. 指定された道路IDから道路データを取得する。
2. `edge.TryTraverse(CurrentNodeId, out next)` で現在地から通れるか確認する。
3. 通れた場合だけ、道路IDと次の地点IDをそれぞれ末尾へ追加する。

`TryTraverse` は接続と通行方向を調べる。道路が遠くにある、または一方通行を逆向きに使う場合はfalseを返す。
失敗したときはルートを変えず、画面に理由を返す。

### Undo・Clear・TryReplace

- `Undo` は道路と地点を1つずつ末尾から削除する。これで現在地も1つ戻る。
- `Clear` は道路を空にし、地点を最初の店舗だけにする。
- `TryReplace` は推奨ルートを使う操作。別の仮ルートで全道路を確認し、成立する場合だけ現在のルートを置き換える。
  不正な推奨を受け取っても、プレイヤーが描いたルートを途中まで消してしまわないための作り。

### GetTime：道1本ずつの時間を足す

```csharp
edgeIds.Sum(id => map.GetTravelTime(id, skillLevel))
```

`Sum` は合計するLINQのメソッド。各道路IDを所要時間へ変換し、その合計を返す。
配達員が変われば同じ道順のままスキルだけ変えて計算し直せる。

### BuildCompletion：完了してよいか確認

配達員と注文が選択されていて、道路が1本以上あり、対象配達先をすべて訪問し、店舗へ戻っている場合だけ完了データを返す。
途中で店舗に戻ること自体は禁止しない。2件の配達先を訪問する間に店舗を挟んだ場合は `Individual route`、
店舗を挟まず回った場合は `Combined route` と表示する。
最初に余計な往復をしても、実際の配達先間の動きで分類する。

## 2. RoadPathfinder：参考になる経路を計算する

このファイルは当初のM3予定に含まれていなかった追加部分。
自由な道路網で推奨を1件出す要望に対応するために導入した。

`FindShortestPath` が「2地点間」、`Suggest` が「注文の配達先を回る全体」、
`GetIndividualReferenceTime` が「個別配達をした場合」を担当する。

### FindShortestPathの主な変数

| 変数 | 内容 |
|---|---|
| `outgoing` | 各地点から出られる道路の一覧 |
| `distance` | 出発地から各地点までに見つかった最短時間 |
| `queue` | これから調べる地点。所要時間が小さいものから取り出す |
| `previous` | その最短時間で到着したとき、直前の地点と道路はどれだったか |

Dijkstra法の流れは次のとおり。

1. 出発地点を0秒としてqueueへ入れる。
2. queueから時間が最も小さい地点を取り出す。
3. そこから出られる道路を調べ、「ここまでの時間＋その道路の時間」を計算する。
4. より短い到着時間が見つかったらdistanceとpreviousを更新し、queueへ入れる。
5. 目的地に到着したら、previousを逆にたどって道路IDの順番を復元する。

たとえば「A→Cが20秒、A→Bが5秒、B→Cが2秒」なら、A→B→Cの7秒を選ぶ。
通れない場合はnullを返す。往路と復路は別々に探索するので、一方通行も反映できる。

`getTime` は「道1本を何秒として扱うか」を渡す関数。
道路の距離だけで決めず、交通量と選択配達員のスキルを含められる。
`serial` は同じ時間の候補をqueue内で別々に保存するための連番で、時間の計算には使わない。

### Suggest：推奨は1件、適用は任意

注文2件なら、配達順は「A→B」「B→A」の2通りを調べる。
各区間と帰り道をFindShortestPathで求め、全体が最短の1件を返す。
画面の推奨ボタンを押したときだけ、ManualDeliveryRoute.TryReplaceへ渡す。

### GetIndividualReferenceTime：個別配達の比較基準

```text
店舗 → A → 店舗
店舗 → B → 店舗
```

各往路と各復路を最短時間で求め、合計する。
手動ルートと同じ配達員・交通量・スキル補正を使う。
配達先Aへの往復で配達先Bを通る経路でも、この基準ではAの注文だけを持った個別配達として数える。

画面では、この基準と「店舗へ帰還済みの自作ルート」を比べる。
作りかけのルートは残りの道を含まないため、節約時間の判定をまだ出さない。

## 3. 今回の学習範囲と追加分

M3の中心は「道順を作る → 時間を計算する → 個別配達と比べる → 完了する」。
先にManualDeliveryRouteと、UIからの呼び出しを読むと全体が追いやすい。

- `MapDefinition` はマップ情報をコードから別データへ移す拡張用。現在のサンプルは指定なしで動く。
- 一方通行は `MapEdge.Bidirectional` と `TryTraverse` が担当。現在のサンプル道路はすべて双方向。
- Dijkstra法は推奨と参考時間の計算用。自分で道を選ぶ操作を置き換えるものではない。

これらは当初M3から広がった範囲として区別する。次の機能追加をする前に、現在の道順記録と比較表示を確認する。
