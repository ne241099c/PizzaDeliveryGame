# Unity・Script・GameObject構成の改善点

記録：2026-10-23、Codex。ユーザーの「Scriptに寄せすぎている部分を改善点としてまとめる」という依頼に基づく整理。当初は文書化のみ。その後、ユーザーの改善実装依頼に基づき、末尾の実装記録へ進めた。

## 目的

Unity上で見た目や調整値を変更でき、変更した箇所とゲームの動作の関係を学びやすくする。既存のゲームルールを維持して、配置・表示・計算の担当を整理する。

コードによる生成がすべて問題なのではない。固定の画面配置と、注文数などに応じて変化する処理を分ける。

## 置き場所の方針

| 内容 | 主な置き場所 | Scriptが担当する部分 |
|---|---|---|
| 固定の画面階層、ボタン、背景、作業台の枠 | Scene・Prefab | 画面切り替え、操作の接続 |
| 位置、大きさ、アンカー、余白、並び | RectTransform・Layoutコンポーネント | 必要な場合の画面サイズへの対応 |
| 共通の色、文字サイズ、フォント、余白の基準 | UITheme | 共通スタイルの適用。個別Prefabとの上書き関係を明示 |
| カード、伝票、窯、配達員レーンの見た目 | 再利用するPrefab | 必要数の生成、対象データの設定、内容更新 |
| 焼き時間、配達速度、費用、確率など | InspectorのSerializeField、必要に応じて設定用ScriptableObject | 設定を使った計算・状態更新 |
| 注文の残り時間、能力、進捗、所持金 | 表示部品をPrefabに用意 | 現在値の表示と更新 |
| 調理の遷移、事故抽選、配達、得点、経営ルール | Script | ゲーム処理そのもの |
| 道の生成、ルート線、移動する印など | Scriptと描画コンポーネント | 動的な生成・描画・移動。線の幅や色などは設定として分離 |
| 確認・撮影・Prefab初期生成の補助 | Editor・Tests・Tools | 通常プレイから分離 |

Inspectorから変更できても、処理自体はScriptが実行する。設定と処理を分けることが目的であり、Scriptをなくすことは目的ではない。

## 改善する順番

### 1. 固定UIの配置と見た目をPrefabへ移す

- 固定の座標・サイズ・文字・画像を大量に組み立てる処理を洗い出す。
- 営業画面の厨房・配達指示・レーンと、スタッフ・求人・設備のカードを優先する。
- 実行時はPrefabを使い、Scriptは内容更新と操作の接続に集中する。
- 動的に増える注文・従業員は、見本Prefabから必要数を生成する。
- 既に進んでいるカード・BusinessViewのPrefab化を再利用し、ゼロから作り直さない。レビュー時点では関連PrefabやScriptに未コミット変更があるため、実装・検証済みの範囲は担当者の最新記録で確認する。

**完了の目安**：Prefabで位置・大きさ・画像を変更すると、Playでも反映される。起動処理が古い固定値へ戻さない。

### 2. 生成ツールと、Unity上で編集するデータの関係を整理する

- Prefab生成ツールを再実行すると手修正が消える箇所を明示する。
- 生成ツールは初期作成・明示的な再生成の用途とし、通常のPlayで再生成しない。
- 日常の配置調整はPrefabでできる形を基本とする。テーマで管理する値は、その適用範囲を説明する。
- Inspectorの参照を使えるところは、GameObject名や子の並びで探す処理を減らす。

**完了の目安**：どこを編集すれば変更が残るかが分かり、意図しない再生成で手修正が失われない。

### 3. 大きなScriptの役割を分ける

- `BusinessView`：厨房表示、地図入力、配達員レーン表示などを、独立した担当へ段階的に分ける。
- `CookingManager`：調理状態、内勤の割り当て、窯キュー、品質・作り直し判断の境界を整理する。
- 表示側はゲーム処理の公開APIを呼び、表示のために計算式を複製しない。
- `partial`でファイルを分けただけでは同じクラスのままなので、役割と参照関係も見直す。
- まず時間の単位や計算の入口を共通化し、動作確認できる単位で分離する。一括での書き直しはしない。

**完了の目安**：配置変更で配達計算を触る必要がなく、調理ルール変更で画面生成コードを読む必要が少ない。

### 4. GameObjectの管理オブジェクトを整理する

- `GameManager`に集中している約26個のScriptを、経営・厨房・配達などの子オブジェクトへ整理することを検討する。
- 名前の例は`CampaignSystems`・`KitchenSystems`・`DeliverySystems`。分けるためだけの細分化は避ける。
- 移動前にInspector参照と`GetComponent`などの同じGameObjectに依存する処理を確認する。
- Title／Gameのシーン分離、MapRootとUIの分離は維持する。
- 背景消去用カメラと編集時の地図見本は役割があるため、重複と決めつけて削除しない。

**完了の目安**：HierarchyとInspectorから各機能の担当を探せる。参照切れ・二重起動・初期化順の不具合がない。

### 5. 調整値と検証を整える

- 時間・費用・確率などの調整値をInspectorに集め、単位と効果をTooltip等で示す。
- 共通設定を複数のSceneやScriptで使う必要がある場合に、設定用ScriptableObjectを使う。
- Prefabの必須参照、画面切り替え、ボタン接続と、変更したゲーム処理の検証を行う。
- 検証は変更箇所に絞る。文書更新や小さな配置変更だけで長時間シミュレーションを回さない。
- 検証・撮影は通常セーブと最高記録を保護し、開始前に実ファイルのバックアップも取る。ハッシュ比較だけを復元手段にしない。

## 先行レビューで見つかった要確認事項

以下はレビュー時点の指摘。別担当が並行して変更中なので、修正前に最新コードと照合し、既に解決したものは再実装しない。

| 優先度 | 指摘 | 改善の方向 |
|---|---|---|
| 高 | セーブの読み込み失敗から新規ゲームに進み、元ファイルを上書きする経路 | 読み込み失敗時は元ファイルを保持する。タイトルの簡易判定とゲーム側の完全検証の差も扱う |
| 中 | 自動作り直しの予測に、実配達で使う時間倍率が入っていない | 配達予測と実配達を同じ時間単位で扱い、間に合う・間に合わない境界を検証 |
| 中 | 最高記録のJSONは読めても、売上文字列などが壊れていると表示時に例外になる | 値も検証し、記録の破損でタイトル全体を止めない |
| 中 | 作り直し・窯キュー・メニュー・生成街の専用検証がTest Runnerの通常一覧から漏れている | 実行対象を明確にし、短い検証を登録する。長時間シミュレーションとは分ける |

## Editor用コードの改善点（追加依頼）

`Assets/Editor`のコードは、このプロジェクト用に追加した開発ツール。Editor専用で通常のゲームビルドには含まれないが、実行するとScene・Prefab・ファイルを変更できるため、改善対象に含める。全体の書き直しはせず、以下を優先する。

| 優先度 | 対象 | 改善点・完了の目安 |
|---|---|---|
| 高 | `Reviews`・`Validation`・`Simulation`と撮影補助 | 検証開始前に通常セーブ・最高記録の実ファイルをバックアップする。準備・全フレーム・例外時の片付けまで保存を抑制し、シーンを読み直しても保護が続く。終了時に前後比較し、差異があれば成功扱いにしない。ユーザーが操作した可能性がある場合は原因を断定せず、勝手に古いデータへ戻さない |
| 中 | `Builders`（`ScreenPrefabs`・`TitleViewBuilder`等） | PrefabやSceneのどの部分を生成・上書きするかを明示する。手修正を残す編集方法を整理し、通常のPlayでは再生成しない。未保存の作業を黙って破棄・保存せず、再生成の対象を限定する |
| 中 | Test Runnerへの接続 | 作り直し・窯キュー・メニュー・生成街などの短い専用検証を実行対象として整理する。「全テスト成功」が何を含むか分かるようにし、長時間シミュレーションは別の実行対象にする |
| 中 | 検証の準備と片付け | 変更した乱数シード、時計、描画停止、Gameビューのサイズ等を、失敗時にも後片付けする。ゲームの正しさを確認する検証と、配置・参照を確認する検証を分ける。旧UI名や古い固定値を前提にした検証は最新仕様へ更新する |

これらは改善候補であり、すべてが現在も未修正という意味ではない。並行作業で保存ロック・Prefab化・検証登録が変更されているため、担当者の最新差分と確認結果を先に調べる。

ゲーム本体の固定UIをPrefabへ移す整理を進めつつ、セーブ保護は検証・撮影を使う前に確認する。Editor用という理由だけで安全とは判断しない一方、文書追記だけでUnity操作や全検証は実行しない。

## 今回の作業範囲

この文書の追加と、Editor用コードの改善点の追記を行った。ゲームコード・Scene・Prefab・調整値は変更せず、Unity操作・検証実行・pushは行っていない。Unity操作の担当はWorkboardの最新記録に従う。


## 改善実装の対応（2026-10-23、進行中）

Claudeの既存Prefab化を維持し、BusinessViewの変更箇所だけをEditor APIで更新する。全画面の再生成は行わない。ピザの描画はPizzaVisualへ分離し、道路表示の計算はRoadGeometryへ共通化。スクロール入力はScrollNavigation、空欄と荷物のドラッグ判別はDragSourceに集約する。

Prefabの再生成は対象・上書きを明示し、旧Prefabをバックアップする。GameManagerの各管理コンポーネントは同じGameObjectへの依存を調べ、参照を付け替えるEditor移行ツールで分野別に整理する。

読み込み失敗時のセーブ上書き、破損した最高記録の金額、自動作り直し予測の時間倍率も修正対象に含める。確認結果と実際に適用できた範囲はHandoff/Current.mdおよびResultsの記録を正とする。CookingManagerの処理全体の再設計などは一括で行わず、既存ルールの維持を優先する。
