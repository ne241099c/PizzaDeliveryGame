# M3締め記録と次段階の優先順位

確認日: 2026-10-21

## 結論

M3は「道順を自分で組み、配達員スキルを含む所要時間を個別配達の参考時間と比べる」段階として締める。
実装は `f418e77` に保存済み。今回の締めではPlay確認結果と次段階の方針を記録する。

時間経過・自動注文・期限・到着時の得点判定はM4で実装する。今回はそのコードを追加していない。
面白さについては、選択の材料ができたことと、十分なゲームとして成立したことを区別する。

## Playで遊んだ結果

Unity Editor 6000.2.10f1のSampleSceneをPlay。
Codexが注文2件・配達員を選び、`NEXT ROADS`の画面ボタンを1本ずつ操作して道順を作った。
推奨ルートの適用や、ルートデータを直接書き換える方法は使わなかった。

地図へのマウス入力の外部注入は今回のセッションでは道路選択を再現できなかったため、道路候補ボタンを使用した。
地図の直接クリックの手動確認はユーザー環境で引き続き確認する。これを今回のPlayで通過したとは扱わない。

選んだ道順:

```text
Store → N1 → N2 → Goal1 → Goal2 → N2 → N1 → Store
```

| 配達員・選んだ道 | 自作ルート | 個別参考 | 個別からの短縮 |
|---|---:|---:|---:|
| Minato 0.9・N1–N2は往復とも大通り | 7.33秒 | 13.12秒 | 5.79秒 |
| Ren 0.3・N1–N2は往復とも大通り | 7.33秒 | 14.07秒 | 6.73秒 |
| Ren 0.3・N1–N2は往復とも裏道 | 8.42秒 | 14.07秒 | 5.65秒 |

個別参考は、同じ配達員が各注文を別々に最短で往復する時間の合計。
表示上の丸め前に計算するため、表示値の差と最終桁がずれることがある。

### 1. 自作ルートで参考時間より速くできるか

できた。Goal1から店舗へ一度戻らずGoal2へ進むことで、手動の大通りルートでも参考時間を短縮できた。
候補から選ばず、道路の接続を順番に選ぶ操作で成立した。

### 2. Renで裏道を選ぶと遅くなるか

同じ巡回順・同じ配達員で、大通り7.33秒から裏道8.42秒へ約1.09秒遅くなった。
N1–N2の1回分では大通り約1.67秒、裏道2.21秒で、往復2回の差が合計へ反映される。
スキル差は画面の秒数と選択の結果で確認できる。ただし実移動を待つ処理がないため、待ち時間としての体感はまだない。

### 3. 「どう回れば得か」を考える面白さ

**Codexによる操作・判断構造の評価: 小さなルートパズルとしての判断はあるが、ゲームとしての緊張感はまだ弱い。**
人の主観的な楽しさを確認したユーザーテストの代わりにはしない。

- まとめて回る、別の帰り道を使う、配達員に合わせて道路を変える、という選択の結果が秒数に出る。
- 今の5地点ではまとめ配達が強く、Renで裏道を使っても個別参考より十分速い。
- Goal1とGoal2の訪問順は、この対称な道路網では最短総時間に差がつきにくい。
- 発生から約310秒経過し、データ上のTimeLimitが60秒の注文2件でも満点200点で即時完了した。期限フィールドは存在するが、現状では判定に使われていない。効率を選ぶ結果が勝敗へまだつながっていない。
- 分岐で道路候補のスクロールが必要だった。完全リアルタイム化後には操作負担も評価する。

「まとめて効率を取るか、期限の近い1件を先に出すか」という競合が次に必要。
ここはマップの見た目やBGMを追加しても埋まらないため、M4を優先する。

## M4の優先順位: 時間のあるゲームとして成立させる

| 順番 | 作ること | その段階の確認条件 |
|---|---|---|
| M4-0 | 必要最小限のUI整理・参照の設定 | 時計、注文残り時間、配達員状態を表示する場所を確保。UI全体の改修で次を長く止めない |
| M4-1 | 共通のゲーム時計と営業時間 | ルート編集中も時計が進み、営業時間が減る |
| M4-2 | 注文の自動発生と期限表示 | 一定間隔で注文が増え、個別の残り時間が減る |
| M4-3 | 即時完了を出発・移動・帰還へ置換 | 出発後はルートを固定。配達員が実際の所要時間を使い、複数人が並行して働く。帰還まで再出発不可 |
| M4-4 | 配達先への到着時に得点確定 | 期限内なら満点、遅延秒数に応じて得点低下。2件目が遅れる判断も発生する |
| M4-5 | 閉店、簡易結果、推奨で出発 | 閉店後は新規注文を止め、配達中の帰還を待ち、得点・配達数・遅延数を表示 |
| M4-6 | 実際に遊んで調整 | 常にまとめが有利にならず、個別を急ぐ場面ができるかを確認 |

M4-3の移動は、既存の地点・道路に沿って位置や進捗が分かる最小表現にする。演出の作り込みは後回し。
Play中生成UIのScene実体化は学習と調整に役立つが、時間・期限の検証とは切り分けて小さく進める。

### 調整用の初期案（この締めでは未実装）

- 営業時間300秒、注文間隔25秒±30%、配達員3人を出発点とする。
- 移動時間には倍率5を掛け、画面の残り時間・期限・到着時刻と単位を合わせる。
  Unityの `Time.timeScale` と混同しない、移動所要時間用の係数として扱う。
- 1件の得点は `max(0, 100 - 遅延秒数 × 5)`。早着ボーナスは最初に足さない。
- 到着した注文から得点を確定し、店舗への帰還は配達員の再利用条件にする。
- お金・コスト・日をまたぐ経営はM5へ残す。

### M4着手前に仕様を揃える点

1. **期限の最短時間は誰のスキルを基準にするか。** 最短往復×倍率×係数1.8という案には、基準配達員の指定が必要。
   最短で走れることだけでは、待機時間や配達員不足も含めて必ず間に合う保証にはならない。
2. **0点の注文の扱い。** 未出発のキャンセルと、出発済み注文の扱いを分ける。出発済みを消して配達員を即帰還させない。
3. **推奨の目的。** 現在の推奨は最短総時間なので、同じ条件で手組みが速度で必ず上回れる前提にはしない。
   期限の近い配達先を先にするなど、「総時間」と「期限内の得点」を別の判断にする。
